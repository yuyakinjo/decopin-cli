# 決定と理由 (ADR)

decopin-cli の設計で「なぜそうしたか」だけを置く。**挙動そのものは書かない** —
挙動は実装とテストが答えで、ここに書くと必ずずれる。

- 使い方 → [README.md](../README.md)
- 挙動の約束 → `test/contract/` (表はそこにしか無い)
- 個々の API の理由 → 公開シンボルの JSDoc

理由は「決めた時点の事実」なので腐らない。同じ議論を最初からやり直さないために残す。

---

## ADR 1: 自作の軽量レンダラーを使う (Ink は使わない)

JSX を再帰的に ANSI 文字列へ変換するだけで足りる。Ink は yoga-wasm を含み起動が
100ms を超え、CLI としては過剰。静的な出力に reconciler は要らない。

**代償**: 対話的 UI (プロンプト・スピナー) は自前で作ることになる。v1 では扱わない。

**関連**: `src/renderer/`。パイプラインは 評価 → レイアウト → 直列化 → 書き出し の 4 段。

## ADR 2: argv と stdin をファイルで分ける

`argv.tsx` と `stdin.tsx` を別ファイルにする。stdin は argv と性質が違う:

- 読むと**入力が来るまでブロックする** (端末で実行するとフリーズする)
- 実行時に有無が変わる (パイプ / リダイレクト / 端末)
- 一度しか読めない

「このコマンドは stdin を読む」という宣言を必須にし、宣言がないコマンドは stdin に
一切触らない。ファイルの有無でそれを表すのが、規約ベースでは一番分かりやすい。

## ADR 3: ファイル名は POSIX 用語で統一する

`argv.tsx` / `stdin.tsx` / `command.tsx` (stdout) / `error.tsx` (stderr) が
シェルの入出力と 1:1 対応する。シェルを学びながら書く人にとって、
「今書いているファイルはシェルのどの口か」が名前で分かる利点が大きい。

`params.tsx` のような一般語は、環境変数や設定ファイルの値も含みうる曖昧さがある。

## ADR 4: v1 は静的出力のみ

装飾 (色・枠・表) の表現力に投資し、対話性は後回しにする。1 回描画して終了する
出力に絞ると、パイプ・リダイレクトとの相性も良い。

## ADR 5: ビルド時にルートを生成する

`app/` を走査して route manifest とエントリを生成し、単一の `dist/index.js` にする。
起動が最速で、配布も 1 ファイルで済む。実行時にディレクトリを走査しない。

## ADR 6: バリデーションは valibot

軽量 (zod の約 1/10) で tree-shaking が効き、起動時間に有利。Standard Schema 準拠。

## ADR 7: `layout.tsx` を導入する

上位ディレクトリの layout が子コマンドの出力を包む。共通のテーマやヘッダを
一箇所で定義できる。Next.js とのアナロジーが完成する。

## ADR 8: `--help` は宣言から自動生成する

`argv.tsx` / `stdin.tsx` の宣言を唯一の情報源にする。スキーマと help の
二重管理が起きない。足りない場合だけ `help.tsx` で上書きする。

## ADR 9: 型はビルド時の codegen で配る

**JSX 式は型引数を運べない。** TypeScript 7.0.2 で実測した:

```tsx
declare function Option<N extends string, T>(p: {
  name: N;
  type: T;
}): Node<{ name: N; value: T }>;
const a = <Option name="loud" type={true as boolean} />;
//    ^? any (JSX.Element 未宣言時) / JSX.Element (宣言時) — 型引数は消える
```

自作 jsx-runtime で `jsx()` factory の戻り値をジェネリックにしても変わらない。
props 方式でも children 方式でも同じなので、**JSX で型を運ぶ設計は選択肢にならない**。

代わりに Next.js の typed routes と同じく、ビルド時に `.decopin/types.d.ts` を生成し、
module augmentation で `Routes` / `EnvVars` を埋める。`command.tsx` は
`CommandProps<'hello'>` で引く。

**代償**: `decopin dev` を回していないと型が古い。未生成のときは緩い型に
フォールバックするが、「古い」と「未生成」は区別できていない。

## ADR 10: schema は `Type.*` の children で組み、valibot は露出しない

利用者が valibot の書き方を覚えなくて済むようにする。`Type.Array` のように
型が再帰する場合に children の入れ子が自然に効く。valibot への依存は
`src/validation/` に閉じ込める。

**valibot に変換層を寄せなかった理由** (実測):

| 試したこと                                                     | 結果                                                                                   |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `v.pipe(v.string(), v.transform(Number), v.number())` に `"3"` | ✅ `3` になる                                                                          |
| `v.optional(schema, 1)` に `undefined`                         | ❌ `Invalid type: Expected string but received 1` — **既定値も wrapped schema を通る** |
| `"abc"` のエラーメッセージ                                     | ❌ `Invalid type: Expected number but received NaN`                                    |
| `v.check` の message 関数で元の値を出す                        | ❌ `received null` (元の文字列が残らない)                                              |

決定的なのは 2 つ目。利用者は `default={1}` と書くのが自然なのに、内部が文字列
パイプになると数値の既定値が弾かれる。だから **変換 → 検証の 2 段構え**を維持する。
`--flag` の存在・`--no-flag`・繰り返しによる配列化も argv の性質であって型の話ではない。

**エスケープハッチ**: `<Stdin mode="json" schema={...}>` だけ生の valibot を受ける。
深い JSON を `Type.Object` / `Type.Field` で書くと 3 階層で 9 行になるため。
argv / env には用意しない (型を失う道を増やさない)。

## ADR 11: argv の検証は middleware より前

middleware が検証済みの `args` / `options` を受け取れる方が実用上の価値が大きい
(`--verbose` による分岐など)。

**代償**: env / argv の検証エラーは middleware を通らない。middleware での
ロギングや計測は「コマンドが実際に実行される場合のみ」走る。

一方 **stdin の読み取りは middleware の内側**に置く。`next()` を呼ばずに
打ち切れば標準入力を消費しないで終われる。

## ADR 12: 配布は単一ファイル + 「評価のみ」遅延

`bun build` は動的 import を同一ファイル内の遅延評価ラッパーにインライン化するため、
「実行されないコマンドを**読み込まない**」ことは実現できない。遅延されるのは
モジュール本体の**評価**のみで、トップレベルのパースは全量走る。

真の遅延読込には `--splitting` (複数ファイル配布) が必要だが、v1 は配布の単純さを取る。

**実測** (Apple Silicon / Bun 1.4、`bun run bench`):

- 総時間 12〜14ms。うち `bun` 自体のプロセス起動が 4.7ms、decopin の取り分が 7.7〜8.9ms
- **コマンド数の影響は小さい**。1 コマンドだけの app でも取り分は 6〜8ms
- `--minify` の効果は 0.4ms 程度。**パースは律速でない**
- valibot の初期化 +1.8ms、renderer 一式 +2.6ms (ソースからの import を個別に測ったもの)
- valibot を遅延 import する実験は、計測の揺れ (±1.5ms) に埋もれて差が出なかったので採用していない

目標の「10ms 未満」は decopin の取り分としては達成、総時間としては未達。

## ADR 13: middleware は `children` ではなく `next` を受け取る

`layout.tsx` の `children` は React と同じ「値」で、置くだけで済む。対して
middleware は「コマンドの実行を包んで、終わったあとに何かする」ためのものなので、
**呼ぶまで走らない関数**でなければ成立しない (時間を測る・後片付けをする・
例外を捕まえる、が全て `next()` を呼び終えた後にしかできない)。

同じ `children` という名前で「値」と「関数」の 2 種類を使い分けさせると覚えることが
増えるだけなので、React の語彙を借りず Koa / Hono / Express と同じ `next` にする。

## ADR 14: 外に出るものは英語、内側の記録は日本語

| 対象                                                    | 言語   |
| ------------------------------------------------------- | ------ |
| CLI の出力 (`--help`、エラー文、`decopin build` の出力) | 英語   |
| 生成されるファイル (`.decopin/`) のヘッダーとコメント   | 英語   |
| README                                                  | 英語   |
| コード内のコメント / このファイル / テスト名            | 日本語 |

境界は**利用者の手元に届くかどうか**。公開したときにそのまま使えることを優先する。
生成物は利用者のリポジトリに残るし、README は npm で最初に読まれる。

内側の記録を日本語のままにしているのは、書く速さと精度が保守の質に直結するため。
英日の併記はしない (2 つの文書は必ずずれる)。

## ADR 15: 仕様書を持たず、契約はテストに置く

以前は `docs/SPEC.md` (1266 行) に挙動の表・props 一覧・ファイル規約の詳細を
書いていたが、**書いてあるのに実装されていない機能が 9 件**発生した。仕様を書く側と
実装する側が別のタイミングで動くと、動かないドキュメントは必ずずれる。

そこで役割を 3 つに分けた:

| 中身           | 置き場所                        | 崩れない理由                   |
| -------------- | ------------------------------- | ------------------------------ |
| 挙動の約束     | `test/contract/` の表駆動テスト | 実行される                     |
| 使い方         | `README.md`                     | 例をテストで実行する           |
| 決定と理由     | このファイル                    | 決めた時点の事実なので腐らない |
| API 個別の理由 | 公開シンボルの JSDoc            | 実装の隣にある                 |

**この方針で捨てたもの**: 節番号による横断参照 (`§4.8` など)。代わりに ADR 番号と
テストファイルのパスで参照する。

## ADR 16: 決定を守る仕組みをテストに置く

ADR 15 で「契約はテスト、理由はここ」と決めたが、**このファイル自体が
形骸化する**という失敗の仕方が残る。性質の違う 2 つをテストで守る。

| 守りたいこと                                    | 手段                           |
| ----------------------------------------------- | ------------------------------ |
| 決定が**破られていない**                        | `test/docs/decisions.test.ts`  |
| 参照が**切れていない** (ADR 番号・テストのパス) | `test/docs/references.test.ts` |

**エディタや CLI のフックには置かない。** Claude Code のセッション中しか効かず、
人が直接編集したときや CI では働かないため。テストなら全員に効き、ずっと残る。

### ADR には守り方を必ず付ける

`test/docs/decisions.test.ts` は ADR 番号ごとに守り方を持つ。

- `lint` — このファイルの中で形を検査する (valibot の閉じ込め、メッセージの言語など)
- `test` — 別のテストが担保している (そのファイルの実在も確認する)
- `manual` — 機械では守れない。理由を書く

**ADR を足すと「分類されていない」で落ちる。** 守り方を決めるまで通らないので、
「決めたが誰も守っていない ADR」が生まれない。逆に ADR を消すと「分類が孤立して
いる」で落ちる。

### 落ちたときに直すのはコードとは限らない

決定そのものが変わったのなら、**直すのは decisions.md**。テストが「決定を
見直す」きっかけになるのが狙いで、それが ADR を生きた文書に保つ。

## ADR 17: 公開は「別ディレクトリを組み立てて」出す

npm に出すのは `publish/` に組み立てたもので、リポジトリの `package.json` は
開発用 (exports が `src/*.ts` を指す) のまま触らない。

**なぜ組み立てるか**: 開発中は自己参照 (`decopin-cli`) が `src/` を指していないと、
テストが古いビルド結果を見てしまう。かといって `exports` を `lib/` に向けると
開発のたびにビルドが要る。`publishConfig` で `exports` / `bin` を差し替える案は
**npm 11 で効かないことを実測で確認した** (`npm pack` したマニフェストが元のまま)。

**中身は tsc が出す JS + .d.ts**。ファイル構成のまま出し、バンドルしない
(利用者が一部だけ import したときに全部を読み込ませないため)。

**それでも Bun は必須**。`Bun.build` / `Bun.stdin` を呼んでいるので、JS にしても
Node では動かない。`engines.bun` で明示する。そもそも生成される CLI 自体が
`#!/usr/bin/env bun` なので、Bun 前提であることに矛盾はない。

**認証は Trusted Publishing (OIDC)**。長期の `NPM_TOKEN` を secrets に置かない。
`--provenance` で来歴も付く。タグと `package.json` の version が食い違ったら
公開前に落とす (公開してからでは取り消せないため)。

## 実測メモ: この設計で踏んだ落とし穴

後から同じところを踏まないために残す。

- **`v.pipe()` は基底スキーマの浅いコピー + `pipe` 配列**で、入れ子の pipe は
  平坦化されない。1 段しか見ないと
  `v.pipe(v.pipe(v.string(), v.transform(Number)), v.minValue(0))` の transform を
  取りこぼして誤った型 (`string`) を出す。`pipe[0]` を再帰的に辿る必要がある
- **Bun は SIGINT のハンドラが無いと exit 0 で終わる**。シェル慣習の 130 には
  ならないので、生成する `entry.ts` で明示的に配線する
- **`tsconfig.json` はコメントと末尾カンマを許す (JSONC)**。素の `JSON.parse` は
  実在する設定で落ちる
- **利用者のプロジェクトに `jsxImportSource` が無いと React を探しに行く**。
  `Could not resolve: react/jsx-runtime` という原因の分かりにくい失敗になるので、
  ビルド時に警告する
- **`String.length` は表示幅と合わない**。日本語 2 桁・絵文字 2 桁・結合文字 0 桁を
  自前で数えないと罫線や表がずれる
- **生成されるファイルは利用者のリポジトリに残る**。`.decopin/` のヘッダーや
  コメントも「フレームワークが出すもの」なので英語で書く (ADR 14 のリントが
  この不整合を実際に見つけた)

## 未決 / 保留

**決めていないこと**をここに置く。ADR ではないので、`test/docs/decisions.test.ts`
の分類の対象にはならない。決まったら ADR に昇格させる。

- 型が**古い** (生成済みだが宣言と食い違う) 場合は素直に型エラーになる。未生成の
  ときのフォールバックは実装したが、「古い」と「未生成」は区別できていない。
  `decopin dev` を回す運用でしのいでいる
- `<Type.Object>` / `<Type.Field>` は 3 階層で 9 行になる。深い JSON では
  `schema` prop を勧めるが、内省できないノードがあると型が `unknown` に落ちる
- `<Arg variadic>` と `<Type.Array>` は別物 (前者は位置引数を複数取る、後者は
  1 つの値が配列) だが、生成される型が両方 `string[]` になり混同しやすい
- ADR 11 の代償 (env / argv の検証エラーが middleware を通らない) が実用上
  問題になるなら、計測・ロギングの責務を `global-error.tsx` に寄せる形を検討する
- 起動時間は総時間 12〜14ms で、目標の 10ms は未達 (ADR 12)。さらに削るには
  6〜8ms が何に使われているかのプロファイルが要る
- middleware の `args` / `options` は `Record<string, unknown>` のまま。middleware は
  複数コマンドにまたがるので、生成された型を当てるには「そのディレクトリ以下の
  コマンドの union」が必要
- `<Table>` のセルは文字列だけで JSX を入れられない。セルに色を付けたい要望が
  出たら `Cell` に `{ text, style }` の形を足す
